# AWS Cost Exporter v1.0.0 Requirements Design

## Status

Approved design for the v1.0.0 implementation plan.

Baseline:

- Source branch: `master`
- Baseline source commit: `ab5ed43a0787738066b227b364616efb64913963`
- Current stable release: `v0.3.0`
- Design date: 2026-07-30

## Summary

AWS Cost Exporter v1.0.0 is a production-stability release. It stabilizes the
existing v0.3 configuration, Prometheus metrics, HTTP API, runtime architecture,
and release artifacts rather than adding another AWS data collector.

The release establishes:

- a SemVer-governed public contract for all v1.x releases;
- documented single-replica operation and recovery behavior;
- a supported capacity envelope and measurable exporter SLOs;
- compatibility, resilience, performance, and leak regression tests;
- a public threat model and least-privilege security guidance;
- reproducible supply-chain verification and release audit evidence;
- complete upgrade, rollback, backup, scaling, and operations guidance.

v1.0.0 does not add leader election, Kubernetes Lease coordination, shared
cache, persistent snapshots, or new business collectors.

## Goals

1. Make the current v0.3 external behavior the stable v1 public contract.
2. Prevent accidental breaking changes through machine-verifiable fixtures.
3. Define and validate a production capacity envelope of 20 targets and at
   least 20,000 business series.
4. Verify predictable partial-failure, restart, shutdown, upgrade, and rollback
   behavior.
5. Publish security and supply-chain assurance appropriate for financial
   telemetry software.
6. Raise core domain, cache, scheduler, AWS client, and limiter test coverage to
   at least 85% without lowering the repository-wide coverage baseline.

## Non-goals

- New Cost Explorer, Organizations, Budgets, commitment, anomaly, CUR, Athena,
  or tag collection capabilities.
- Active-active or active-passive high availability.
- Kubernetes Lease, leader election, distributed target ownership, or static
  target sharding managed by the exporter.
- Shared cache, database, object-store snapshot, or local snapshot persistence.
- Built-in authentication, authorization, or TLS termination for HTTP paths.
- Compatibility adapters for v0.1 or v0.2 configurations and metrics.
- A redesign of the v0.3 provider, domain, scheduler, cache, or metric model.

## Selected Approach

Three product directions were considered:

1. **Stability-first:** freeze and verify the v0.3 contract, formally support a
   single replica, and invest in SLOs, resilience, security, tests, and release
   evidence.
2. **Limited HA:** add Kubernetes leader election while also stabilizing the
   contract.
3. **Distributed HA:** add shared refresh coordination or shared snapshots.

The selected approach is stability-first. It keeps AWS paid requests bounded,
avoids a new distributed-systems dependency at the 1.0 boundary, and turns the
already broad v0.3 feature set into a supportable production contract.

## Architecture Boundary

The following v0.3 architecture remains authoritative:

- AWS and Athena work runs only in background collectors.
- `/metrics` reads an immutable aggregate snapshot and never triggers AWS or
  Athena requests.
- Collector results are isolated by `CollectorID`.
- Cache publication uses copy-on-write partial replacement and atomic snapshot
  publication.
- Scrapes are lock-free and traverse immutable data without copying complete
  business slices.
- A failed collector retains its last successfully published partial snapshot.
- Other targets, collectors, and providers continue refreshing independently.
- AWS SDK initial attempts and retries pass through global and target rate
  limiters while preserving SDK retry, backoff, and retry-token behavior.
- Context cancellation terminates limiter waits, AWS requests, Athena polling,
  scheduler backoff, and workers.

Internal implementations may change to fix correctness, security, performance,
or stability defects, but the external v1 contract defined below must remain
compatible.

## Stable v1 Contract

### Compatibility Policy

All v1.x releases are backward compatible with v1.0.0.

- Metric names, types, label sets, label meaning, units, and bounded label value
  enums cannot be removed, renamed, or semantically changed.
- Configuration keys, types, defaults, validation, environment-variable
  references, and runtime meaning cannot be removed or incompatibly changed.
- HTTP paths, supported methods, status codes, content types, and response
  semantics cannot be removed or incompatibly changed.
- Only additive optional configuration with a safe default is allowed in a
  minor release.
- Only additive metrics that do not change existing series are allowed in a
  minor release.
- Removal, renaming, or incompatible semantic changes require v2.0.

Deprecation must be documented in the Wiki, release notes, and an appropriate
runtime observable signal. A deprecated contract remains available for at
least two minor releases and at least six months, whichever is longer.

An urgent security or data-correctness issue that requires a compatibility
break needs a dedicated security advisory, an explicit migration procedure,
and maintainer approval. It cannot be treated as an ordinary minor change.

The compatibility promise begins at v1.0.0. No v0.1 or v0.2 compatibility
layer is required. The v0.3 contract is adopted directly as the v1.0 baseline,
without adding `config_version`.

### Configuration Contract

The seven top-level configuration sections remain:

- `server`
- `log`
- `aws`
- `targets`
- `collection`
- `cache`
- `telemetry`

Exact unmarshalling remains mandatory. The v1.0 fixture records all nested
keys, value types, defaults, environment-variable references, validation
ranges, required/optional status, and runtime semantics. `--check-config` and
production startup continue to use the same validation and environment
resolution path.

Contract tests must reject any incompatible fixture difference and must prove
that the checked example configuration can enter production startup without a
second configuration rejection.

### Prometheus Contract

The v1.0 fixture records every production metric descriptor:

- metric name;
- metric type;
- ordered variable labels and constant labels;
- unit and semantic meaning;
- bounded enum values where applicable.

HELP text may be clarified when the underlying meaning does not change. It
cannot be used to redefine a metric. Existing protections against unbounded
labels remain mandatory, including no anomaly IDs, plan or reservation IDs,
account email, raw AWS error text, or unconstrained tag values.

Queries and documentation must retain `target`, `provider`, `cost_basis`, and
`currency` where relevant. Different currencies, providers, or cost bases must
not be summed by default.

### HTTP Contract

The stable paths remain:

- `/metrics`
- `/healthz`
- `/ready`
- `/version`

The HTTP fixture records accepted methods, normal and error status codes,
content types, response schema or body semantics, and cache behavior. In
particular:

- `/metrics` only reads the current snapshot;
- `/healthz` reports process liveness and is independent of AWS credentials,
  AWS APIs, and Athena;
- `/ready` reports required Cost Explorer data readiness and staleness;
- `/version` reports the release version and build identity without secrets.

### Release Contract

Official binary archives support:

- Linux `amd64` and `arm64`;
- macOS `amd64` and `arm64`;
- Windows `amd64` and `arm64`.

The official container image supports Linux `amd64` and `arm64`. The Helm OCI
chart officially supports single-replica Kubernetes deployment.

The release contract includes six platform archives, SHA-256 checksums,
archive SBOMs, a multi-architecture container image, a Helm OCI chart, keyless
signatures, and provenance/attestation. Contract tests compare future release
configuration against the v1.0 asset manifest.

## Availability, Recovery, and Upgrade Behavior

### Readiness and Partial Failure

- `/healthz` remains successful while the process can serve HTTP, even when AWS
  credentials or external services fail.
- `/ready` depends only on all enabled Cost Explorer collectors of required
  targets having succeeded and remaining within the configured stale limit.
- Optional targets and Organizations, Budgets, commitments, anomalies, CUR,
  Athena, and tag collectors do not participate in readiness.
- A collector failure retains that collector's previous successful partial
  snapshot.
- Other targets and collectors continue to refresh and publish.
- Stale data remains visible through `/metrics` together with status and age
  metrics, while readiness and alerts identify the stale required data.

### Shutdown

On a termination signal, the process must:

1. transition to not-ready;
2. cancel scheduler work and limiter waits;
3. cancel AWS requests, SDK retry waits, Athena polling, and backoff timers;
4. wait for workers within the configured shutdown timeout;
5. shut down the HTTP server;
6. exit without leaked workers or background goroutines.

The sequence is verified with deterministic cancellation and goroutine cleanup
tests.

### Single-replica Deployment

The supported Helm deployment keeps `replicaCount: 1`. The default Deployment
strategy is cost-first rolling replacement:

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 0
    maxUnavailable: 1
```

Old and new pods therefore do not overlap and cannot duplicate scheduled paid
Cost Explorer or Athena requests during a normal upgrade. This strategy permits
a temporary metrics outage. It is explicitly documented as single-replica
recovery, not HA.

The new pod becomes ready only after all required Cost Explorer collectors
complete their first successful refresh. The implementation does not add a
Lease, shared cache, or cross-pod coordination.

### Upgrade, Rollback, and Backup

- Run `--check-config` with the new binary before rollout.
- Upgrade from v0.3.0 to v1.0.0 uses the existing v0.3 contract directly.
- Pin production releases by immutable image digest and chart version.
- Roll back using the previous image digest and Helm revision.
- Runtime snapshots are memory-only, require no migration, and are rebuilt
  after restart.
- Backup covers configuration, Secret references and independently protected
  Secret values, IAM policies, Helm values, dashboards, and alert rules.
- Backup examples and repositories never contain actual credentials,
  ExternalId values, tokens, or real billing data.

## Capacity and SLO

### Supported Capacity

The v1.0 supported envelope is:

- up to 20 configured targets;
- up to 1,000 business series per target under documented cardinality limits;
- at least 20,000 business series in one process;
- one exporter replica;
- a reference allocation of 2 vCPU and 512 MiB memory.

Configurations beyond this envelope may work but are not part of the v1.0
performance commitment. Operators must use series limits, tag allowlists,
overflow behavior, refresh intervals, and AWS/Athena request budgets to remain
inside the envelope.

### Exporter SLO

Within the supported envelope and reference allocation:

- `/metrics` p99 response time is less than 5 seconds;
- `/metrics` request success is at least 99.9%;
- a 24-hour stability run shows no sustained growth in RSS, Go heap,
  goroutines, or open connections;
- `/metrics` makes zero AWS and Athena requests;
- graceful shutdown leaves no collector worker behind.

AWS and Athena availability, permission correctness, billing-data freshness,
and upstream response latency are external dependencies and do not count as an
exporter implementation SLO failure. Their effects must still be observable
through bounded request, retry, duration, refresh failure, collector status,
and snapshot age metrics and documented alerts.

The stability report must state the workload generator, series distribution,
scrape interval, CPU and memory limits, Go version, host environment, and
pass/fail calculations so the result is reproducible.

## Security Design

### Threat Model

The public threat model identifies at least these protected assets:

- AWS access keys, secret keys, session tokens, profile files, assumed-role
  credentials, and ExternalId values;
- cost, budget, commitment, anomaly, account, CUR, and tag data;
- CUR database, table, workgroup, S3 paths, and Athena result paths;
- GitHub tokens, build credentials, release signatures, and provenance;
- configuration and IAM policies that can redirect signed AWS requests.

Trust boundaries are explicit:

- configuration files and environment variables are trusted administrator
  input;
- AWS, STS, Organizations, Budgets, Cost Explorer, and Athena responses are
  external input and require strict parsing and bounds;
- `/metrics` is sensitive financial telemetry;
- the build service and release identity form a supply-chain trust boundary.

Endpoint overrides remain available for local and end-to-end tests. The
documentation must warn that a malicious override can receive signed requests;
write access to exporter configuration is therefore equivalent to authority to
use the configured AWS credentials.

### Deployment Security

The exporter does not add built-in HTTP authentication or TLS in v1.0.
Production deployments must restrict access with network policy, security
groups, private services, reverse proxies, or monitoring namespace controls.
Direct public Internet exposure is unsupported.

The official container remains non-root, uses a read-only root filesystem,
drops all Linux capabilities, disallows privilege escalation, and does not
mount a Kubernetes ServiceAccount token by default.

Credential values, ExternalId values, role credentials, raw AWS responses,
account email, and unbounded error text cannot enter logs, error responses,
metrics, debug output, ConfigMaps, examples, test fixtures, or release audit
records.

IAM guidance is separated by capability: base identity/STS, Cost Explorer,
Organizations, Budgets, commitments, anomalies, CUR/Athena, Athena results,
and required S3/Glue access. Each section provides a least-privilege policy and
an audit checklist.

### Vulnerability and Security Response

CI performs secret scanning, dependency and Go vulnerability scanning, static
analysis, container scanning, Helm/Kubernetes security validation, and pinned
GitHub Action verification.

Critical and High findings block release unless fixed or covered by a public,
time-bounded, traceable risk acceptance that records exploitability, exposure,
mitigation, owner, and expiry. Findings cannot be silently ignored.

`SECURITY.md` documents supported versions, private reporting, acknowledgement
and response targets, coordinated disclosure, and the procedure to revoke or
replace affected release artifacts.

## Supply-chain Release Audit

Every stable release produces a repository-tracked audit record containing:

- tag and exact source commit;
- release workflow run URL and immutable workflow revision;
- complete release asset manifest;
- container manifest and per-platform digests;
- Helm OCI chart digest;
- SBOM and provenance presence;
- cosign version, certificate identity, OIDC issuer, and verification commands;
- vulnerability scan results and any approved risk acceptance;
- checksums and final GitHub Release state.

GitHub Actions are pinned to immutable commit SHAs. Release jobs use least
privilege. Images and the Helm OCI chart are signed with cosign keyless signing,
and provenance/attestation is generated by the build workflow.

The Release remains a draft until a maintainer verifies the audit evidence and
publishes it. Verification commands in the audit must work without access to
private repository secrets.

## Test and Verification Plan

### Contract Tests

- Golden configuration schema and semantic fixture.
- Golden Prometheus descriptor fixture, including ordered labels and bounded
  enum values.
- Golden HTTP method, status, content type, and response behavior fixture.
- Golden release platform and asset manifest.
- A compatibility-diff test that classifies additions and rejects incompatible
  changes.
- Example configuration validation through `--check-config` and the production
  startup validation path.

### Core Correctness and Resilience

- Core domain, immutable snapshot, cache, scheduler, AWS client, and limiter
  coverage of at least 85%.
- Repository-wide coverage at or above the v1.0 planning baseline.
- Tests for authorization failure, throttling, timeout, retry exhaustion,
  invalid pagination, malformed responses, Athena failure/cancellation,
  context cancellation, and shutdown timeout.
- Three-target isolation tests covering simultaneous success, authorization
  failure, and timeout.
- Old-data retention and independent collector publication tests.
- Readiness tests for required, optional, disabled, failed, and stale
  collectors.
- Goroutine, worker, connection, and timer cleanup tests.

### Metrics and Cardinality

- Golden exposition tests for all production metrics.
- Duplicate label-set rejection tests.
- Fixed label ordering and bounded operation, reason, status, provider, basis,
  and collector values.
- Tag overflow amount-conservation tests.
- Assertions that no credential, ExternalId, account email, anomaly ID, plan
  ID, raw AWS response, or raw error becomes a label or output value.
- Assertions that every scrape performs zero AWS/Athena calls.

### Performance and Stability

- A deterministic 20-target, 20,000-plus-series benchmark fixture.
- `/metrics` p50, p95, and p99 latency measurement under the documented scrape
  concurrency.
- `testing.AllocsPerRun` verification that immutable snapshot traversal does not
  introduce allocation growth proportional to the number of series.
- A 24-hour stability workflow or documented release-gate job capturing CPU,
  RSS, heap, goroutines, connections, garbage collection, scrape latency, and
  scrape errors.
- Pass/fail evaluation against the supported capacity and exporter SLO.

### Packaging and Deployment

- `go test ./...`
- `go test -race ./...`
- `go vet ./...`
- repository-pinned golangci-lint
- container smoke tests for supported image platforms where runners permit
- promtool rule tests
- Grafana dashboard validation
- Helm lint and render tests
- kubeconform or equivalent Kubernetes schema validation
- security-context and single-replica rollout strategy tests
- v0.3.0 to v1.0.0 upgrade, first-readiness, and Helm rollback test

### Real AWS Release Candidate Validation

A maintainer runs the release candidate with documented least-privilege IAM
against representative Cost Explorer and enabled optional-provider paths. The
public evidence records only scenario, result, timing, and sanitized error
category. Credentials, account identifiers, billing values, SQL, raw responses,
and private resource names are not recorded.

## Documentation Deliverables

README, bilingual Wiki, ROADMAP, release notes, Helm documentation, and release
verification records must consistently describe:

- the v1.x compatibility and deprecation policy;
- the stable configuration, metric, HTTP, and release contracts;
- supported platforms and capacity envelope;
- single-replica behavior and expected upgrade outage;
- readiness, partial failure, stale snapshots, shutdown, and restart behavior;
- SLO definitions and upstream dependency exclusions;
- upgrade, rollback, backup, and restore procedures;
- AWS and Athena request-cost controls;
- threat model, endpoint override risk, metrics access controls, and
  least-privilege IAM;
- release asset, SBOM, provenance, signature, and verification procedures.

The Wiki continues to describe the current stable release only. Policy files
such as `SECURITY.md` remain authoritative at their existing repository paths.

## Acceptance Criteria

v1.0.0 is complete only when all of the following are true:

1. Configuration, metrics, HTTP, and release contract fixtures exist and pass.
2. No v0.3 external contract is unintentionally broken.
3. Core domain, cache, scheduler, AWS client, and limiter coverage is at least
   85%, and repository coverage has not regressed.
4. The documented resilience and graceful shutdown scenarios pass under race
   detection.
5. The 20-target, 20,000-plus-series workload meets the `/metrics` SLO in the
   2 vCPU / 512 MiB reference environment.
6. The 24-hour report demonstrates no sustained resource or goroutine growth.
7. The default Helm rollout prevents overlapping exporter pods and documents
   the expected temporary outage.
8. The v0.3.0 to v1.0.0 upgrade and rollback procedure is reproduced.
9. The public threat model, least-privilege IAM guidance, and security response
   policy are complete.
10. The release audit verifies checksums, SBOMs, provenance, image and chart
    digests, signatures, and vulnerability scan disposition.
11. README, Wiki, ROADMAP, dashboards, alerts, and release notes agree on the
    v1.0 contract and operating limits.
12. Acceptance evidence is stored in the repository and can be reproduced; an
    oral or unrecorded manual confirmation is insufficient.

## Assumptions

- The v0.3 contract represented by the stated master baseline is suitable for
  direct stabilization.
- AWS and Athena behavior can vary by account and region; exporter SLOs isolate
  upstream failures while preserving their observability.
- The documented reference capacity is a supported envelope, not a hard parser
  limit beyond existing configuration cardinality safeguards.
- A temporary metrics outage during a single-replica upgrade is preferable to
  duplicate paid AWS requests.
- Snapshot persistence and coordinated HA remain candidates for a later major
  design, not implicit v1.x requirements.
